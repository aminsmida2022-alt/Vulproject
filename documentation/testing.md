## S1 - Scan, enrichment, prioritization

**Steps:** `scanner/scan_all.sh` then `python3 scripts/enrich.py`.

**Expected:** one Trivy report per asset; findings deduplicated, enriched with
EPSS + KEV and ranked by P.

**Observed:**

| Item | Value |
|---|---|
| Scan time (3 images, offline DB) | 2 min 50 s |
| Unique findings | 917 |
| EPSS scores retrieved | 821 |
| KEV-listed findings | 4 |
| P1 / P2 / P3 / P4 / P5 | 3 / 12 / 157 / 549 / 196 |

Top 3: CVE-2019-10149 on db-server (99.5, KEV), CVE-2023-4863 on web-server
(93.0, KEV), CVE-2023-44487 on web-server (89.8, KEV).

## S2 - Ticket creation + deduplication

**Steps:** POST `findings.json` to the n8n webhook, twice.

**Expected:** one ticket per P1/P2 finding with priority/KEV labels and SLA due
date; the second run creates nothing.

**Observed:** run 1 created 15 tickets (#3-#17): 3 P1 (due +7 days), 12 P2
(due +30 days), KEV label on the 4 KEV findings. Run 2: still 16 issues in
the repo (15 + 1 older test ticket) -> 0 duplicates.

**Bug found and fixed:** the first version of the workflow failed with
`ExpressionError: Multiple matches found` as soon as more than one finding was
eligible (item pairing broken by the dedupe HTTP node). Dedupe was moved into a
single Code node; the workflow was retested with the 15 real findings.

## S3 - Remediation verified

**Steps:** patch the web server (`nginx:1.18.0` -> `nginx:1.28.0` in the
inventory), then `scripts/verify.py` on its 6 tickets (#4, #7, #9, #10, #12, #14).

**Expected:** rescan proves the CVEs are gone -> tickets closed with evidence.

**Observed:** 6/6 closed with label `verified-fixed`; each ticket received an
evidence comment (image ID, scan time, Trivy DB date, report SHA-256) and an
evidence file in `tickets/evidence/`.

## S4 - Verification fails

**Steps:** without changing the image, click *Verify* on ticket #9 in the
dashboard (also run on #14 from the CLI).

**Expected:** ticket stays open, labelled `verification-failed`, comment lists
the vulnerable package still installed.

**Observed:** as expected, e.g. #14: `libnghttp2-14 1.36.0-2+deb10u1 (fixed in
1.36.0-2+deb10u2)` still detected. Dashboard run took ~1 min (detached
process, live log in the UI).

## S5 - Regression

**Steps:** roll the web server back to `nginx:1.18.0`, rescan, enrich, POST to n8n.

**Expected:** the 6 tickets closed in S3 are reopened, not duplicated.

**Observed:** #4, #7, #9, #10, #12, #14 reopened with label `regression`
(and `verified-fixed` removed) and a "Regression detected" comment. No new ticket.

## S6 - SLA escalation + risk acceptance

**Steps:** set the due date of #3 (P1) and #2 to yesterday; add `risk-accepted`
+ justification comment on #2; trigger `POST /webhook/sla-check`.

**Expected:** #3 escalated; #2 ignored.

**Observed:** response `{"issue":3,"action":"escalated"}`; #3 got labels
`sla-breached` + `escalated` and an escalation comment; #2 untouched.
